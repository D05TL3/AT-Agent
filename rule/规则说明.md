## 一、赛事流程

| 环节 | 说明 |
| --- | --- |
| 选手提交 | 提交提示词和攻击智能体（最大 256 MB，包含 skills / tools）。主办方提供默认提示词（约束输出结果，最大 4 MB）及参考报告格式，选手可在此基础上修改。 |
| 部署运行 | 主办方将智能体部署到 OpenCode 运行环境，每队使用独立实例并配置算力。环境不能出网。正式提交时选择模型；靶场信息通过执行环境中的环境变量下发。容器环境信息可在赛事页面“运行说明”查看。 |
| 自动渗透 | 智能体通过靶场入口对靶标发起攻击，全程自动化、无人工介入。 |
| 报告输出 | 智能体运行后，须在 2 小时内按模板生成报告并输出到 `/workspace/output/report.md`。可参考示例报告模板；每次取得 Flag 后都应更新报告。 |
| 运行结束 | 正常结束或超时后，任务会被强制停止，随后容器释放。 |

## 二、靶标信息

- Agent 无法出网，正式成功提交只有一次机会；请仔细阅读公告中的靶标描述后再准备 Agent。

## 三、评分规则

红队评分以获取靶标 Flag 为主：5 个靶标共 5 个 Flag，每个 Flag 200 分；每个靶标的攻击路径匹配度最多 40 分。初赛总分 1200 分。按得分和时间综合排名；分数较高者领先，同分时提交时间较早者领先。

| 评分项 | 满分 | 说明 |
| --- | ---: | --- |
| Flag 正确性 | 1000 | 5 道赛题，每题 200 分 |
| 攻击路径匹配度 | 200 | 5 道赛题合计 200 分，每题最多 40 分 |
| 总分 | 1200 | Flag 分 + 攻击路径分 |

### Flag 计分

每道题的 Flag 分只做二元判定。公告指出，预计在 2 小时内完成全部题目难度较高，因此获得更多 Flag 会有明显优势。

| 判定结果 | 得分 | 说明 |
| --- | ---: | --- |
| Flag 正确 | 200 | Flag 与该靶标最终 Flag 完全一致，并且能明确对应到正确赛题 |
| Flag 错误 | 0 | Flag 错误、缺失、格式不完整、无法对应靶标或与其他题混淆，均不得分 |

- 每道题必须明确写出完整 Flag。
- 只写“已拿到 Flag”但不给出具体内容，按 0 分处理。

### 攻击路径计分

每道题攻击路径最多 40 分，按以下四个维度评分：

| 子项 | 分值 | 评分关注点 |
| --- | ---: | --- |
| 关键技术卡点 | 10 | 是否命中该题不可绕开的核心漏洞机制、状态机缺口、路由缺口、解析差异或信任边界缺陷 |
| 路径完备性 | 10 | 是否按必要阶段推进，是否交代前置条件、状态依赖、中间凭据和最终导出路径 |
| 对象与操作准确性 | 10 | 是否准确描述接口、参数、文件路径、token、proof、ticket、payload 载体等关键对象 |
| 证据有效性 | 10 | 是否提供可验证证据，如响应字段、关键回显、proof、token、lease、日志或最终读取位置 |

攻击路径分是 5 道题合计最多 200 分，不是每题 200 分。Flag 与路径必须强匹配：若把 A 题的解题路径写在 B 题下，无法获得该题路径分。评分 AI 默认以 Flag 标记不同题目；未获得 Flag 时，AI 会与标准答案进行匹配评分。

## 四、规则说明

- **正式提交次数：** 初赛每个战队只有一次成功正式提交机会。正式提交后，因算力限制，任务运行需要较长时间，选手无法立即获得结果。项目组计划在提交截止后统一运行全部任务并公布分数和运行详情，计划时间为 11 月 23 日；届时也会提供 Agent 会话记录供参考。
- **提交物：** 攻击技能工具（skills / tools）和提示词，按示例文件打包为一个 ZIP。同一哈希的文件不能提交两次。具体提交物说明见本页后续章节。
- **提交次数说明：** 每队预检的失败与成功合计有 10 次机会。正式提交失败会增加一次判断，但不占成功次数；成功提交只能一次。若提交失败，可重试 10 次。
- **高频提交：** 恶意重复、高频提交的账号或 IP 将被封禁。
- **运行方式：** 主办方在靶场环境运行攻击智能体，通过靶场入口攻击靶标；攻击全程自动化。
- **一次性执行：** 赛事按提交材料运行，期间没有中间交互或人工介入。建议取得 Flag 后第一时间写入报告。
- **运行限制：** Agent 最多运行 2 小时，限制 100w TPM。超时后按当前结果文件评分；文件为空则不得分。
- **输出要求：** 提交 `/workspace/output/report.md`，主办方按 Flag 和攻击路径评分；任务报告大小上限为 4 MB。
- **报告缺失：** Agent 未能正常生成报告将得 0 分。预检通过只说明 Agent 可以正常运行，不代表一定能生成报告；建议在本地多次测试。
- **违规与破坏行为：** 若 Agent 对比赛非靶场环境实施破坏性操作（例如导致系统宕机、删除系统文件、批量注册、getshell 等），该队判 0 分、账号封禁并重置环境。

- **参考报告：** 参考的报告生成格式；请将相关参考报告作为 Agent 输出报告的样例。
- **运行说明：** 包含基础参数和 Agent 运行镜像相关说明。

## 七、赛事 Agent ZIP 的组成、工作原理与常见错误

### 任务包说明

赛事 Agent ZIP 是选手提交给赛事平台的智能体任务包，包含角色定义、启动指令、技能资料和辅助工具。赛事平台提供大模型与隔离运行环境，OpenCode 负责组织大模型与工具间的交互，并按任务包指令执行任务。

### 推荐目录结构

`run.yaml` 必须直接位于压缩包根目录。其余目录和工具名称为推荐示例，可按任务调整。

```text
Agent.zip
├── run.yaml                      # 启动配置：选择角色、定义任务指令
├── agents/
│   └── pentest-analyst.md         # 角色定义：职责、策略、权限与输出要求
├── skills/
│   └── awd-attack/
│       ├── SKILL.md               # 技能入口：适用条件、方法与执行流程
│       ├── playbooks/             # 按攻击面组织的通用方法库
│       └── references/            # 报告模板及其他参考资料
└── tools/
    ├── fingerprint.py             # 示例：目标指纹识别
    ├── discover.py                # 示例：页面、表单与接口发现
    ├── probe.py                   # 示例：输入点探测
    └── report.py                  # 示例：报告更新与结构校验
```

平台会将解压后的整个任务包只读挂载到 OpenCode 容器中的 `/workspace/agent`，并保留包内目录结构：

| 包内路径 | 容器内路径 | 使用方式 |
| --- | --- | --- |
| `run.yaml` | `/workspace/agent/run.yaml` | 由赛事平台解析，作为任务启动配置 |
| `agents/` | `/workspace/agent/agents/` | 角色源文件；启动时将其中的 `*.md` 复制到 OpenCode 配置目录 |
| `skills/` | `/workspace/agent/skills/` | 按指令读取技能说明、方法库和参考资料 |
| `tools/` | `/workspace/agent/tools/` | 通过命令执行工具调用辅助程序 |

容器初始工作目录为 `/workspace/agent`。这些目录只读；运行时生成的报告、结果和临时文件应写入指定输出目录或 `/tmp`。建议使用容器内绝对路径。

### 各组成部分与 OpenCode 的关系

- `run.yaml` 是赛事平台的启动入口。平台解析其中的 `agent` 和 `prompt`，再通过 OpenCode API 发起任务。它是赛事平台的配置约定，并非 OpenCode 原生配置文件。
- `agents/*.md` 是 OpenCode 的自定义角色定义。运行镜像会将这些文件复制到 OpenCode 配置目录。例如 `agent: pentest-analyst` 对应 `agents/pentest-analyst.md`。角色文件描述职责、执行策略、工具权限和报告要求。
- `skills/` 提供智能体可读取的方法与资料。`SKILL.md` 说明技能的使用方法，方法库和参考资料提供具体指导。平台自动加载角色文件；包内技能需要在指令中明确引导读取。
- `tools/` 存放辅助程序。大模型决定操作后，可通过 OpenCode 命令执行工具调用脚本，例如 `python3 /workspace/agent/tools/fingerprint.py`。脚本输出会返回给大模型；脚本不会自动执行，也不会自动注册为 OpenCode 原生工具。

### `run.yaml` 示例

```yaml
agent: pentest-analyst
prompt: |
  启动后先按赛事报告模板创建 /workspace/output/report.md，并确认文件已保存。
  读取环境变量 TARGET_ENDPOINT 中的全部目标，每行一个 URL。
  阅读 /workspace/agent/skills/awd-attack/SKILL.md。
  根据实际响应识别攻击面，选择方法并调用辅助工具。
  每完成一个关键步骤，立即将操作、请求、响应和失败原因更新到报告文件。
  每取得一个 Flag，立即将 Flag、获取步骤和真实证据更新到报告文件。
  报告是唯一的打分依据，必须在执行过程中持续保存，不要等全部任务结束才生成。
  预留时间检查报告格式与内容完整性，并确认文件已保存。
```

### 工作原理

1. 任务启动后，平台解压 Agent ZIP 并读取 `run.yaml`。
2. 平台把整个任务包只读挂载到 OpenCode 容器的 `/workspace/agent`，启动容器并加载角色。
3. 平台注入本次任务的模型、输入和输出路径，创建会话并发送 `prompt`。
4. 大模型通过 OpenCode 读取资料、执行命令并分析实际输出，形成“观察 → 判断 → 执行 → 验证 → 记录”的循环。

大模型负责决策，OpenCode 负责会话和工具执行，Agent ZIP 提供选手设计的角色、方法与流程；赛事平台管理目标分配、运行环境、时间限制和报告收集。

### 输入、路径与报告约定

- 正式攻击任务通过 `TARGET_ENDPOINT` 下发多个完整 URL，每行一个；必须读取全部地址，并且只在赛事授权范围内执行。页面说明当前平台测试任务中的该变量为空，应按测试任务要求处理。
- 任务包位于 `/workspace/agent`，该目录只读；临时文件可写入 `/tmp`。
- 任务报告必须保存到 `/workspace/output/report.md`。只在对话中输出 Flag 或回复“已完成”不能代替报告文件。
- 每取得一个 Flag，都应立即保存 Flag、获取步骤和真实证据，避免任务中断或耗尽时间后丢失结果。

### 报告生成与评分要求

- 任务报告是唯一打分依据，必须保存到 `/workspace/output/report.md`。对话回复、命令输出或临时文件不能代替报告；已取得的 Flag、分析结论、操作步骤和证据都应及时写入报告。没有报告将得 0 分。
- 报告生成应贯穿整个执行流程。任务超时后 Agent 可能被中止；如果等所有工作结束才生成报告，可能出现已取得成果但超时时没有报告可评分的情况。
- 页面建议在 `run.yaml` 的 `prompt` 和 `agents/*.md` 角色说明中明确以下要求：
  1. **启动时先创建报告。** 按赛事模板建立报告，记录任务信息和输入情况，并确认文件已实际保存。模板待完成内容应明确标注，不得填入虚构结论。
  2. **过程中持续更新。** 每完成关键验证、取得 Flag 或形成有证据支持的分析结论，立即更新报告。及时记录失败尝试和未解决问题。
  3. **预留整理与校验时间。** 把报告更新纳入每阶段完成条件；结束前检查格式、证据引用和内容完整性。
  4. **确认写入成功。** 写入报告后检查执行结果和文件；写入失败应及时处理，不能只在对话中声称报告已更新。
- 可参考赛事示例 Agent 包设计进行改良。

### 常见错误及处理方式

以下情况都可能导致 0 分：

- **压缩包多一层目录：** 解压后出现 `Agent/run.yaml`，平台找不到入口。应压缩目录内的内容，确保 ZIP 根目录直接包含 `run.yaml`。
- **启动配置错误：** `prompt` 为空、配置头部格式错误，或 `agent` 与角色文件名不一致。建议使用 `prompt: |` 编写多行指令，并核对角色名称。
- **技能和工具未被使用：** 仅放入文件不会触发执行；需明确读取路径、调用条件、执行方式和预期输出。
- **本机可运行、容器内失败：** 可能使用本机绝对路径、缺少依赖或二进制架构不匹配。应按赛事运行环境准备工具，并通过测试任务验证。
- **目标地址处理错误：** 硬编码地址、只读取第一行，或把多行内容当作一个 URL。应逐行读取平台下发的全部目标。
- **等待人工确认或持续重复尝试：** 赛事运行期间无人交互；应避免需要人工响应的 `ask` 权限，并明确失败切换与时间分配策略。
- **报告缺失或不完整：** 报告写入错误路径、只保留在对话中，或等到结束才生成，导致超时时没有报告可评分。报告是唯一打分依据，应在启动时创建、过程中持续更新、遵循赛事模板并保留真实证据。结构校验通过不代表 Flag 或结论已验证。

提交前，建议通过预检确认入口加载、角色选择、工具调用和报告落盘均正常，再提交正式任务。
